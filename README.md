# Maize Leaf Disease Classifier — Andiza ML Extension

An end-to-end ML pipeline that classifies maize (corn) leaf photos into one of four
classes — `Healthy`, `Common_Rust`, `Northern_Leaf_Blight`, `Cercospora_Gray_Leaf_Spot`
— extending the earlier tabular crop-yield-prediction project into image data, per the
Machine Learning Cycle assignment. Covers data acquisition, preprocessing, model
training, evaluation, a retraining pipeline with an automatic trigger, a FastAPI
service, a monitoring/diagnosis UI, and cloud deployment.

### What's committed to git vs. generated locally

`data/raw/`, `data/train/`, `data/val/`, `data/test/` are **not** committed (large,
regenerable). Everything else is. If you're setting this up fresh:

1. Get the raw maize image data (see "Setup" below).
2. Run the notebook's preprocessing cells (Section 3) once to generate
   `data/train/`, `data/val/`, `data/test/` from `data/raw/`.

## Setup

### 1. Clone and install

```bash
git clone <your-repo-url> crop_disease_indetifier
cd crop_disease_indetifier
python -m venv venv
source venv/bin/activate        # Windows Git Bash: source venv/Scripts/activate
pip install -r requirements.txt
```

### 2. Get the raw data into `data/raw/`

You need `data/raw/Healthy/`, `data/raw/Common_Rust/`, `data/raw/Northern_Leaf_Blight/`,
`data/raw/Cercospora_Gray_Leaf_Spot/`, each full of `.JPG` images. Either:

- Extract the provided `maize_raw_data.zip` into `data/raw/`, **or**
- Re-download via sparse git checkout (see the commented-out block in the notebook's
  Section 1, "Data Acquisition").

### 3. Run the notebook once (generates train/val/test + confirms the pipeline)

```bash
jupyter notebook notebook/maize_leaf_disease.ipynb
```

Run all cells top to bottom. This regenerates `data/train/`, `data/val/`, `data/test/`
and the EDA/evaluation charts in `data/`. `models/best_model.keras` is already trained
and committed, so you don't need to retrain to use the API — the notebook re-running
training is for reproducibility/grading, not a prerequisite for the next steps.

### 4. Run the API locally

```bash
uvicorn api.main:app --reload --port 8000
```

Check it's alive: `curl http://localhost:8000/health` → `{"status":"ok",...}`
Interactive API docs: http://localhost:8000/docs

### 5. Open the UI

Open `ui/index.html` directly in a browser (double-click it, or `open ui/index.html` /
`start ui/index.html`). It defaults to `http://localhost:8000` in the API URL field at
the top — change that field if your API is running elsewhere (e.g. the deployed Render
URL).

## How the pieces run together

```
 notebook/*.ipynb  ──trains──▶  models/best_model.keras
                                        │
 src/preprocessing.py                  │  loaded by
 src/model.py         ──imported by──▶ │
 src/prediction.py                     ▼
 src/retrain.py       ──imported by──▶ api/main.py  ◀──HTTP──  ui/index.html
                                        │
                                        ▼
                              Dockerfile / render.yaml
                                        │
                                        ▼
                              deployed Render URL
```

- `src/*.py` are plain importable modules — no dependency on the API or notebook.
  The notebook imports them (via `sys.path.insert(0, "../src")`) instead of
  duplicating logic, and so does `api/main.py`.
- `api/main.py` is the only thing that talks HTTP. It wraps `src/prediction.py`
  (predict, evaluate) and `src/retrain.py` (ingest, trigger, retrain).
- `ui/index.html` is a static file with no build step — it only ever talks to
  whatever URL is in its API field via `fetch()`. It has zero dependency on the
  notebook or `src/` directly.
- The `Dockerfile` packages `src/`, `api/`, `models/best_model.keras`, and
  `data/raw/` into a deployable image (see `DEPLOYMENT.md`).

## Retraining

```bash
# Check whether enough new data has accumulated to warrant a retrain
python src/retrain.py --check-trigger

# Move newly uploaded images from data/incoming/<class>/ into data/raw/<class>/
python src/retrain.py --ingest

# Run a full retrain cycle (re-split, warm-start, train, evaluate, promote-if-better)
python src/retrain.py --run --epochs 3
```

Or via the API/UI: bulk-upload through `POST /upload-retrain-data` (or the UI's
"Upload & Retrain" tab), then trigger `POST /retrain`.

## Load testing (flood simulation)

`locustfile.py` simulates concurrent users hitting `/predict`, `/health`, and
`/model-info`. Full methodology, honest caveats, and raw CSVs are in
`LOCUST_RESULTS.md`; summary:

| Scenario | Concurrent users | Median | p95 | Throughput | Failures |
|---|---|---|---|---|---|
| 1 worker, 10 users | 10 | 150ms | 380ms | 4.93 req/s | 0% |
| 2 workers, 10 users | 10 | 150ms | 340ms | 5.02 req/s | 0% |
| 1 worker, 20 users | 20 | 400ms | 820ms | 8.12 req/s | 0% |

Zero failures across all scenarios — the API queues gracefully under load. Worker
count showed negligible improvement in this test environment (single CPU core);
`LOCUST_RESULTS.md` explains why and gives the command to re-run this against the
real multi-core Render deployment for a more representative container-scaling
comparison.

To re-run:
```bash
uvicorn api.main:app --host 0.0.0.0 --port 8000 &
locust -f locustfile.py --host http://localhost:8000 \
    --users 10 --spawn-rate 2 --run-time 45s --headless --csv locust_results/run1
```
