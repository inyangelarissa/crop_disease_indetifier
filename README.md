# Maize Leaf Disease Classifier

**Machine Learning Pipeline Summative**

**NAMES:** INANGE LARISSA 

An end-to-end machine learning pipeline that classifies maize (corn) leaf photos into
one of four classes — `Healthy`, `Common_Rust`, `Northern_Leaf_Blight`,
`Cercospora_Gray_Leaf_Spot`. This extends my earlier tabular crop-yield-prediction
project (Introduction to Machine Learning module) into image data, covering the full
cycle: data acquisition, preprocessing, model training, evaluation, a retraining
pipeline with an automatic trigger, an API, a monitoring/diagnosis dashboard, cloud
deployment, and load testing.

### What's committed to git vs. generated locally

`data/train/`, `data/val/`, `data/test/` are not committed (regenerable from
`data/raw/`, which **is** committed — Streamlit Community Cloud clones the repo
directly with no build step to copy files in selectively, so the raw dataset needs
to actually be in git for retraining to work on the deployed app).

## Setup

### 1. Clone and install

```bash
git clone https://github.com/inyangelarissa/crop_disease_indetifier.git
cd crop_disease_indetifier
python -m venv .venv
source .venv/Scripts/activate      # Windows Git Bash
pip install -r requirements.txt
```

### 2. Get the raw data into `data/raw/` (if not already present after cloning)

`data/raw/Healthy/`, `data/raw/Common_Rust/`, `data/raw/Northern_Leaf_Blight/`,
`data/raw/Cercospora_Gray_Leaf_Spot/`, each full of leaf images (sourced from
PlantVillage). This is committed to the repo directly, so a fresh clone should
already have it.

### 3. Run the notebook once (optional — a trained model is already included)

```bash
jupyter notebook notebook/maize_leaf_disease.ipynb
```
Run all cells top to bottom to reproduce data acquisition, preprocessing, training,
and evaluation from scratch. `models/best_model.keras` is already trained and
committed, so this is for reproducibility/grading, not a prerequisite for running
the app.

### 4. Run the app locally

```bash
streamlit run streamlit_app.py
```
Opens automatically at http://localhost:8501 — three tabs: Overview, Diagnose,
Upload & Retrain.

### 5. Or just use the live deployment

No local setup needed — see the live app link at the top of this README.

## How the pieces run together

```
 notebook/*.ipynb  ──trains──▶  models/best_model.keras
                                        │
 src/preprocessing.py                  │  imported directly by
 src/model.py         ──imported by──▶ │
 src/prediction.py                     ▼
 src/retrain.py       ──imported by──▶ streamlit_app.py
                                        │
                                        ▼
                          Streamlit Community Cloud
                                        │
                                        ▼
                        https://<your-app>.streamlit.app
```

`src/*.py` are plain importable modules with no dependency on any particular
front end — `streamlit_app.py` imports them directly (no HTTP layer, no separate
server process), and so does the notebook. `api/main.py` (FastAPI) is a second,
independent way to expose the same `src/` modules over HTTP — it still works
(`uvicorn api.main:app --reload`), it's just not the deployed path anymore (see
"Why Streamlit" below).

## Model evaluation

Full detail (confusion matrix, per-class precision/recall/F1, ROC-AUC, misclassified
sample review) is in the notebook. Summary on the held-out test set:

| Metric | Value |
|---|---|
| Test accuracy | 92.9% (baseline), improved after retraining on additional data |
| Macro precision / recall / F1 | 0.901 / 0.900 / 0.900 |
| Macro ROC-AUC | 0.986 |
| Weakest class | `Cercospora_Gray_Leaf_Spot` — visually confusable with `Northern_Leaf_Blight` |
| Strongest classes | `Healthy`, `Common_Rust` |

Two models were compared: a baseline CNN trained from scratch, and a MobileNetV2
transfer-learning model. The baseline CNN was selected for production after the
MobileNetV2 run showed a BatchNorm cold-start instability when trained without
ImageNet pretrained weights, documented and diagnosed in the notebook rather than
hidden, since it's a genuine, explainable finding about transfer learning without
pretrained weights.

## Load testing (flood simulation)

`locustfile.py` simulates concurrent users. Full methodology and raw CSVs are in
`LOCUST_RESULTS.md`; summary (originally run against the FastAPI deployment):

| Scenario | Concurrent users | Median | p95 | Throughput | Failures |
|---|---|---|---|---|---|
| 1 worker, 10 users | 10 | 150ms | 380ms | 4.93 req/s | 0% |
| 2 workers, 10 users | 10 | 150ms | 340ms | 5.02 req/s | 0% |
| 1 worker, 20 users | 20 | 400ms | 820ms | 8.12 req/s | 0% |

Zero failures across all scenarios. Note: these numbers are from the FastAPI/Render
deployment. Streamlit apps don't expose a comparable stateless REST endpoint to
flood-test the same way, so this load test remains the FastAPI service's result —
`api/main.py` is kept in the repo specifically so this test (and the "API creation"
requirement) still has a real, working target to point at.

## Retraining

The retraining pipeline (`src/retrain.py`) ingests newly uploaded, class-labeled
images, re-splits the dataset, warm-starts from the current production model, trains
for a few epochs, evaluates the candidate against the held-out test set, and only
promotes it to production if it's actually better — a retrain can never silently make
production worse.

```bash
# Check whether enough new data has accumulated to warrant a retrain
python src/retrain.py --check-trigger

# Move newly uploaded images from data/incoming/<class>/ into data/raw/<class>/
python src/retrain.py --ingest

# Run a full retrain cycle
python src/retrain.py --run --epochs 3
```

Or through the app's "Upload & Retrain" tab — bulk upload, then click "Retrain now."

## Why I switched the deployment from Render/FastAPI to Streamlit

The original deployment (FastAPI + a custom HTML/JS dashboard, on Render's free
tier) worked for prediction, but retraining repeatedly crashed from
out-of-memory kills. Render's free tier caps a service at 512MB RAM, shared
between the already-running API (which keeps a model loaded to serve
predictions) and a new training job triggered by `/retrain` — two things
needing memory in the same process budget at once.

I tried shrinking the batch size (32→8→4), explicitly releasing the cached
model's memory before training (`tf.keras.backend.clear_session()` — a real
gap, since dropping a Python reference to a Keras model alone doesn't release
TensorFlow's internal graph memory), and one broken detour into changing image
resolution that I had to revert (it silently made the retrain incompatible
with the already-trained model's fixed input shape). These helped, but the
fundamental issue was architectural: **two memory-hungry processes sharing one
512MB budget.**

Streamlit Community Cloud gives roughly 1GB RAM per app, and more
importantly  `streamlit_app.py` is a single process with no separate API
server keeping its own model loaded while a retrain job runs. This removes the
actual failure mode rather than continuing to shrink parameters around it.
`STREAMLIT_DEPLOYMENT.md` has the full reasoning and deployment steps.

I kept the FastAPI implementation (`api/main.py`, `Dockerfile`, `render.yaml`)
in the repo rather than deleting it — it's real, tested, working code, and it's
still what the Locust load test above targets.
